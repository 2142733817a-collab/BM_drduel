Code for the Mount & Blade II: Bannerlord 'DR Duel' server which is a copy of the Mount & Blade Warband Duel system.  
The code was not formatted / refactored etc. since it was created out of curiosity and trying around what is possible while staying Native compatible. It was not supposed to be released at all.

Some small parts (messages / reflections) might be copied by krex his Admin tool or from takeo (cRPG).

## FT3 / FT5 / FT7 scene objects

In a scene running this server's Duel mode, place three weapon-hittable objects with collision and give each object exactly one of these tags:

| Tag | Personal duel mode |
| --- | --- |
| `adimi_ft3_anvil` | First to 3 wins |
| `adimi_ft5_anvil` | First to 5 wins |
| `adimi_ft7_anvil` | First to 7 wins |

Hit an object to select its mode. Hit the same mode's object again to return to FT1; hit another mode's object to switch directly. An object with multiple FT tags is disabled. Use the same hittable entity arrangement as the existing FT7 anvils; entity names do not select the mode. Existing FT7 tags and the script name remain supported.

Both players must select the same win limit to request and accept a duel. The limit is fixed when the duel is accepted and cannot be changed during the series. FT3 means first to 3 wins, not best of 3. The existing `!ft 1` through `!ft 10` commands remain available and follow the same matching rule. FT3, FT5 and FT7 series all announce the final result.

These tags require the server code; Native alone does not implement them. The example scenes are unchanged, so place and label the three objects in your own map before testing in game.

## 传送门标签 1–20

现有服务器代码按 `teleport_door_` 前缀查找路线标签，再按完整标签匹配落点，没有将编号限制为 1–4。因此 `teleport_door_1` 至 `teleport_door_20` 均可沿用现有逻辑；1–4 只是示例地图使用的编号，并非代码上限。

以第 20 条路线为例：

| 对象 | 必须设置的标签 |
| --- | --- |
| 传送门 | `teleport_door`、`teleport_door_20` |
| 独立落点箭头 | `teleport_target`、`teleport_door_20` |

新增编号可使用 `teleport_door_5`、`teleport_door_6`、`teleport_door_7`、`teleport_door_8`、`teleport_door_9`、`teleport_door_10`、`teleport_door_11`、`teleport_door_12`、`teleport_door_13`、`teleport_door_14`、`teleport_door_15`、`teleport_door_16`、`teleport_door_17`、`teleport_door_18`、`teleport_door_19`、`teleport_door_20`。

复制现有可交互门及独立落点后，替换各自原有的编号标签，每个实体只保留一个路线标签。每条路线保留一个有效落点；同号门传送到同号箭头，实体名称不参与配对。落点箭头须保持独立，不能同时带 `teleport_door` 标签。双向通道需要两条路线，例如门 19 指向箭头 19、门 20 指向箭头 20，将两个箭头分别放到对面的出口处。

服务端保留场景里的原版 `CastleGate`、`StandingPoint` 和对象编号，在原版 F 交互验证成功后传送，不再删除并替换这些脚本。缺少、重复或混用路线标签会写入启动日志，使用配置错误的路线会显示中文提示。可交互城门应使用均匀缩放（X/Y/Z 相同，建议 1/1/1）；原版不支持物理对象的非均匀缩放聚焦。骑乘时原版站位交互不可用，须先下马。

`is_section`、`section_a` / `section_b` 与传送编号无关，应根据地图出生区域配置。新增编号的匹配规则已经过源码检查，实际交互、落点朝向和传送效果仍需在服务器中验证。

## 按兵种设置出生点

在场景里复制原有出生点箭头，保留 `spawnpoint` 标签，再给每个点添加以下一个兵种标签：

| 标签 | 选兵类别 |
| --- | --- |
| `spawn_troop_1` | 步兵、重步兵 |
| `spawn_troop_2` | 弓箭手、弩手 |
| `spawn_troop_3` | 骑兵、骑射、轻骑兵、重骑兵 |

同一类别可以放多个点，服务器使用原生出生点评分选择位置。一个点同时有多个兵种标签时，不作为专属点使用；某类别没有有效专属点时，保留原来的分区逻辑：有死亡记录时取原有最近分区出生点，普通入场回到 A 区。仍遵循 `exclude_mounted` / `exclude_footmen`。分类依据是选中的角色类别，不依赖当前手中武器。

正常入场、普通死亡及系列结束后的复活走分类出生点。FT 系列进行中的死亡仍优先使用原有决斗原位复活逻辑。没有改动地图；需要在自己的场景里放置并保存这些标签。

出生位置按所选兵种分类，角色装备保留原版选兵与技能选项的结果，包括头盔、坐骑和远程武器。出生点评分及分区回退根据最终装备是否带马，遵循 `exclude_mounted` / `exclude_footmen`；选兵界面继续使用原版。正式出生、重生和简单／一般 AI 复制的衣服颜色与盾牌旗帜取自玩家选择的国家，不随决斗场队伍配色随机改变；武器架拾取的盾牌也使用该国家旗帜。困难 AI 使用其随机抽中的国家。

## 原版客户端的距离决斗提示

服务器默认每 0.5 秒检查一次距离：超过 55 米隐藏头顶决斗提示，靠近到 50 米以内恢复。50–55 米之间保持上次状态，减少边界反复切换。每次每名观察者最多处理 8 个变化，优先恢复靠近的目标；距离未变化到需要切换时不重复发消息。

玩家不需要安装客户端 Mod。服务器只向对应观察者发送原版消息，使用临时个人对局状态的覆盖与结束来保留目标隐藏缓存，不新增虚假进行中对局行，不改变真实 Team、生命值或位置。每条消息使用独立可靠事件；不能保证原版客户端把整组消息在同一帧显示完毕。

正在准备、进行 FT 系列或有待处理挑战的观察者暂停更新；真实对局中的目标不会因靠近而恢复提示。真实系列结束后重新计算其提示状态；重连和断线会清理对应观察关系。发送异常时停止新的距离更新，并在观察者空闲后尝试恢复原版提示，失败会记入服务器日志并等待下次清理。

AI 预约和训练不属于原版真人决斗消息流程，单独接入隐藏策略：AI 挑战者作为目标时，对其他观察者隐藏头顶决斗信息；作为观察者时，也隐藏周围玩家的可挑战信息。倒计时和 FT 局间保持隐藏，结束后附近目标恢复、远处目标仍按距离隐藏。隐藏机制本身不新增对局条目；实际 AI 挑战另外使用下述独立显示记录。

当前实现保守接受 `area_flag_1` 到 `area_flag_5`（使用编号 0–4）；没有这些有效场地编号时功能自动停用。这不是协议上限：原版该字段为 4 位，可编码 0–15。这里的场地编号与传送门编号 1–20 是不同用途。

设置服务器进程环境变量 `ADIMI_DUEL_DISTANCE_MARKERS=0` 可在下次载入场景时关闭此功能。当前代码验证不包含游戏运行；消息分帧时是否闪出个人面板、多人场景下开销及完整联机效果仍需实际客户端验收。

## 攻击触发的 AI 训练

每组最少放两个独立对象，各自添加一个角色标签和相同的分组标签。例如第 1 组：

| 对象 | 角色标签 | 分组标签 | 是否必需 |
| --- | --- | --- | --- |
| 可被武器击中的触发物 | `adimi_ai_trigger`，另加下述难度标签 | `adimi_ai_group_1` | 任一难度至少一个 |
| AI 出生位置标记 | `adimi_ai_spawn` | `adimi_ai_group_1` | 必需 |
| 预埋在地下的障碍物 | `adimi_ai_barrier` | `adimi_ai_group_1` | 可选 |
| 平时可用、挑战期间旋转放倒的梯子 | `adimi_ai_ladder` | `adimi_ai_group_1` | 可选，可替代该入口的木板障碍 |
| 挂原版 `VolumeBox` 的区域对象 | `adimi_ai_area` | `adimi_ai_group_1` | 可选 |

**没有障碍标签就不做木板上升；没有梯子标签就不做梯子收起；没有区域对象就不检测、驱离其他玩家，也不执行盒子越界判负。** 没有上升障碍和区域对象时，使用下述 5 秒导航网格判负规则；单独配置收梯子不会关闭这条保护。三个可选角色互不依赖，可以只收梯子而不放木板或空气墙。第 2 组统一改为 `adimi_ai_group_2`，之后使用规范的正整数编号。同组每档触发物、AI 出生标记和区域对象各最多一个，障碍和梯子可以有多个；不可在一个对象上混用触发/出生/障碍/梯子/区域角色、多个难度选择标签或多个分组标签。缺少必需角色、同档触发/生成/区域重复或已标记的可选组件配置错误会在日志中说明并停用该组，其余组不受影响。

**三座雕像各自保留原角色和组号，只额外添加一个难度标签：**

| 难度 | 额外标签 | AI 模板和加强规则 |
| --- | --- | --- |
| 简单 | `adimi_ai_trigger_1` | 首次敲击时复制玩家当前兵种、装备、生命上限与护甲 |
| 一般 | `adimi_ai_trigger_2` | 简单模板，有效熟练度 +50，AI 生命上限 ×2 |
| 困难 | `adimi_ai_trigger_3` | 每场从六个原版国家随机选择固定近战步兵模板，有效熟练度 330，模板生命上限 ×2，护甲按下面规则加强 |

同组可放任意一档或三档各一座，共用 AI 出生点、障碍和 Box。旧的 `adimi_ai_trigger` 单独使用仍为简单；旧 `adimi_ai_trigger_enhanced` 对应一般。明确的 `_1`／`_2`／`_3` 优先于旧别名，不能在同一雕像保留两个编号标签。

困难模式不跟随触发者阵营或装备变化。瓦兰迪亚、帝国、库赛特、斯特吉亚、巴旦尼亚选择各自原版重步兵及加强护甲 perk；阿塞莱使用宫廷卫士、原塔巴尔斧和“战场魔神”攻击 perk（步行速度伤害加成 +40%、对盾伤害 +25%，沿用原版条件，不额外换月刃斧）。在所选原版 perk 生效后的每部位护甲上，原值严格大于 50 时加 15，否则加 30。困难 AI 不带马；国家衣服颜色和盾牌旗帜取抽中的国家。随机结果、模板、装备与加强数值在本次预约时固定，整场 FT 不重新抽取、不读取玩家后来换的装备。

三档使用独立的服务端 Agent origin 和模型，不修改共享兵种或玩家技能表。一般与困难的熟练度应用于原版攻速/装填、射击误差、AI 决策和骑术公式；模板原始技能和模型之外的 Athletics 动画步幅不改写。生命翻倍只计算一次，不影响玩家或坐骑生命上限。

首次有效敲击固定本次难度。预约倒计时中继续敲击同档触发物增加 AI 数量；敲另一档不会增加数量或延长倒计时，须等本次挑战结束再切换。三档共享同一预约，不会同时生成多场；FT 替换与局间回血复用已固定的模板，不会逐局累乘。

触发物需要可被武器打击的实体碰撞。服务器自动挂载命中观察器，地图内不需要挂本 Mod 的自定义脚本，也不需要玩家安装客户端 DLL。不要同时保留 FT 铁砧、传送门标签；推荐普通非破坏性物品，避免子实体脚本抢占命中。AI 标记使用独立箭头/空实体，不能带普通玩家出生用的 `spawnpoint` 标签；标记附近需要可行走的 AI 导航网格和足够站位。

敲击一次预约本组并提示 3 秒后生成 1 个 AI；同一玩家继续有效敲击时增加数量，并从最后一次有效敲击重新倒计时 3 秒。0.25 秒内重复命中按一次处理，每次最多 10 个 AI。简单、一般使用首次敲击时玩家的装备快照和相同角色，包含武器架取得的武器与当前坐骑；不是完整复制所有玩家特长效果。困难使用上表固定模板。AI 拥有独立装备，只与触发者敌对、锁定该玩家，不与同组 AI、路人或其他组玩家敌对。

收到尚未接受的真人决斗邀请仍可触发 AI。首次成功预约会移除该玩家收到的服务端待处理邀请；原版客户端旧提示按其 10 秒期限消失，迟到接受不会开启真人对局。自己主动发出的未答邀请，以及已经进入准备、交战或 FT 系列的真人对局仍会阻止触发 AI；一个玩家仍不能同时预约多个 AI 组。

**AI 对局规则：1 对 1 沿用玩家的 FT 设置（铁砧 FT3/FT5/FT7 或 `!ft 1–10`）；1 对 2 个及以上 AI 强制 FT1，一局定胜负。** 规则在首次生成 AI 时固定，系列中修改个人 FT 不影响正在进行的系列，也不会为了多 AI 对局将玩家个人 FT 改成 1。FT3 是先赢 3 局，不是三局两胜。多 AI 局必须击败全部 AI 才算玩家获胜，击败其中一个不会结束；玩家先阵亡则整局失败，同时死亡也按玩家失败结算。

实际 AI 挑战会向空闲旁观者的原版左上对局列表发送显示记录：`[AI简单] 兵种 ×N`、`[AI一般] 兵种 ×N` 或 `[AI困难] 兵种 ×N`，同时更新 FT 比分。显示身份使用独立非真人 ID，不加入服务器真人列表、不挂实际 AI，结束后移除组件和条目；仍需有效的 `area_flag_1` 至 `_5`。挑战者自身保留训练文字提示，避免与隐藏头顶标记的个人面板消息冲突。此功能只使用原版客户端已有消息，当前已进行托管方法和状态回归，完整网络时序及实际 UI 留待实机验证。

AI 挑战计入原版击杀与阵亡，训练逻辑不重复累计。整场胜利另按原真人决斗公式结算一次决斗积分、连胜和赏金；FT 中间局和多 AI 单个击杀不重复结算。失败保留累计积分、清连胜及赏金，三档没有额外积分倍率。取消、断线、换场不计完成；服务器保存逐场日志，未新增数据库长期战绩功能。AI / PvP 共同限制协议不能表示的分数与连胜，正常范围内的奖励公式不变。

1 对 1 的 FT 系列每局单独计分，未达到目标胜场时**只复活败者，保留胜者实体和当前位置**：玩家阵亡时，存活 AI 及其坐骑保留，玩家通过原版流程在本组 `adimi_ai_spawn` 标记处复活；AI 阵亡时，在该标记处生成替代 AI，存活玩家留在当前位置，不拉回首次敲击点。点位被活体占用时选择标记附近有效导航位置，不移动幸存者。双方准备好后，按原服恢复函数补生命、盾牌、箭和弩矢，再友好等待 3 秒后继续交战。等待期间保留区域占用及升起的障碍物，存活 AI 暂停锁定旧玩家，开局时改为锁定复活后的新玩家角色。

玩家复活仍使用本次训练的角色和装备快照，位置优先于普通按兵种/分区出生点；原来的 AI 出生标记直接复用，不增加必需组件。30 秒内未完成复活则取消系列。同时死亡按玩家本局失败计分，两方均死亡时在玩家回来后补出 AI，再共同等待 3 秒。只有整场胜负已定或挑战取消时才清理本组存活 AI、释放区域、下降障碍物；检测区域内的尸体按下述开局/结束清理规则处理，区域外及未配置检测盒子的组保留 10 秒消失配置。

整场 AI 挑战分出胜负后，存活玩家保持原实体和当前位置，按战前快照恢复武器、盾牌与弹药，并按战前生命上限回满血、恢复当前坐骑生命。整场失败且已经阵亡时，自动通过原版流程在对应兵种的普通重生点满状态复活：预览和正式出生都使用战前角色、装备及旗帜，不混入新菜单外观；原版 SpawnEnd 后再补装实际武器，避免出生过滤或回调改写导致装备缺失。装备恢复成功后才消费完成记录，失败每秒重试且不重复回血；已生成角色的装备重试不会再次创建预览或角色。该完成复活记录不使用 FT 局间的 30 秒超时；断线、换队、死亡、其他生成与清场会使旧记录失效。整场完成与未结束的 FT 局间败者复活分开处理，继续保留后者的胜者实体；取消、断线、换队与场景清理不伪装成挑战完成。

障碍物如有设置，需在场景中预先挂好原版 `SynchedMissionObject`（不是城门/可破坏物的派生脚本），设置为可移动的动态实体并保留有效碰撞。地图保存的位置就是地下起始位置。首次敲击后沿**世界 Z 轴向上 3 米，耗时 1.5 秒**；整场对局/FT 系列结束（包含越界判负），或挑战者断线、换队等导致取消后，从当前位置用 1.5 秒回到保存的起点，复位期间不能再次预约。不要给障碍物挂服务端自定义同步脚本或手工修改对象 ID。

**旋转放倒梯子的配置示例：** 给梯子加 `adimi_ai_ladder` 和 `adimi_ai_group_5`，挂原版 `SynchedMissionObject`，设置为动态实体。梯子保存时放在正常可爬的位置，物体原点作为固定梯脚。首次敲击后在 **1.5 秒**内由保存姿态旋转到指定放倒姿态，世界位置保持不动；本次目标数据是编辑器角度 `(X=89.43°, Y=-7.20°, Z=7.08°)`，对应截图中的第5组梯子。地图配置副本的正常姿态是 `(-30.02°, -0.08°, -0.17°)`，不会自动推算水平角度。该目标姿态是本模板的配置数据，其他朝向的梯子应先配置自己的目标数据，不能直接沿用。

整场胜负已定或挑战取消后，用同样1.5秒沿原旋转路径返回；结束时重放保存的完整原始局部变换，恢复位置、朝向和缩放，不累计偏移。FT小局和局间复活不提前立起梯子，恢复完成前不能再次预约。作为替代入口时，原木板及子空气墙可保留，但应移除该入口对应的AI移动标签；其他入口的木板围挡和检测盒继续使用原有规则。中间帧按两端旋转插值，不逐项插值欧拉角，也不把梯子平移到地下。

服务器在梯子首次收起前递归添加原版 `Moveable` 物理标志，保留其 `Ladder` 等既有标志，不启用刚体重力模拟。使用原版消息同步物理标志；晚加入时另定向重申已准备梯子的标志，当前位置仍走原版对象帧同步。地图必须预先有原版同步脚本和稳定场景 ID，服务器不临时补同步脚本；玩家不需要额外客户端 Mod。

同组父子或祖孙障碍都带相同标签时，只移动最上层已标记的父物体，后代保持原有局部位置、旋转和缩放随父级整体移动；子物体不会再单独上升 3 米。父根须有上述原版同步组件，子物体可以保留已有脚本，也可以仅作为普通网格/碰撞子物体。不要把同一移动层级分配给不同训练组。

梯子父子同时标记时也只旋转最高标记根一次；不要在同一移动层级混用上升障碍与旋转梯子角色，两种运动模式或不同组号的嵌套会停用相关组并记录诊断。多个独立梯子可以同组一起动作，但须使用适合各自朝向的目标姿态。

同组多个互不包含的障碍父根会一起升降，每个根独立保存原始变换、计时与重试状态。只有所有障碍完成复位后才允许再次预约。日志记录去重后的根数和随父移动的重复标签数量；不会自动补脚本、改变父子关系或修改地图。

3 米指对象原点从保存位置上移的距离。运动由服务端按 1.5 秒计时，只插值世界 Z，保持 X/Y 和地图保存的旋转、缩放矩阵，不使用 OverTime 消息。最多每 0.05 秒通过原版局部帧接口同步一次；有父对象时，先把目标世界变换转换到父对象的局部坐标，避开已核验 v1.4.8 全局帧消息的 S/F 轴读写顺序错误。最后精确到达目标后停止发送；中途反向则从当前高度移回目标。日志记录起点、目标、终点 XYZ 及完整姿态轴，供实机核对。原版客户端仍使用其原生消息处理和显示流程，不需要客户端 Mod。

区域如有设置，使用原版 `volume_box` 完整对象，保留 `VolumeBox` 脚本，调整范围覆盖挑战区域、触发者和 AI 标记。AI 初次开局和 FT 每局正式开始时，将盒内所有未触发本组的普通玩家移到所有 AI 区域之外的 `spawnpoint`，包括骑乘者；主人保持原位。先验证全部目标点，再执行搬移；缺少符合骑步限制的区域外出生点则取消新挑战，不开始混场战斗。另一场真实 PvP/AI 的参与者不被强行搬走，发现占场则取消本次开局。仅收到邀请不算正在对局，不会让旁观者免于清场。没有 Box 的最简组不执行清人。

开局清场之后，实际交战中仍按旁观者到最近参战玩家/AI 的三维距离判定：3 米内警告、1 米内移至区域外复活点，警告最多每 5 秒一次；不会因远处玩家仅仅进入或靠近 Box 就持续遣返。预约倒计时和 FT 友好等待不持续清场。机器人、坐骑不单独作为旁观者；骑乘玩家搬移时保留并移动当前坐骑，脚本交互会先停止。地图必须保留区域外有效出生点。人与人决斗使用相同 3 米警告、1 米遣返规则。

**AI 挑战开始后，存活的触发者离开本组检测盒子，直接判整场挑战失败，清理本组 AI 和 AI 坐骑并降下障碍物，不继续下一局。** 服务器沿用每 0.25 秒的区域检查；FT 局间倒计时及复活后的准备时间也受此规则约束，越界优先于同次检查中的 AI 死亡结算。判负不伪造双方已赢局数，也不修改玩家个人 FT 设置；死亡角色或等待复活的旧尸体不参与越界判定。首次生成 AI 前的 3 秒预约期离开区域只取消预约。没有区域对象时不执行这些区域检查。

**仅有触发物和 AI 出生标记、同时没有障碍物和检测盒子的组**，另用导航网格防止脱离战斗：挑战中玩家连续 5 秒离开有效 AI 导航网格，整场自动判负并清理本组 AI，提示“你已连续 5 秒脱离 AI 索敌范围，本次挑战自动判负。”回到有效网格后计时清零，死亡或等待复活不累计；FT 局间存活玩家仍需遵守。只要配置了障碍物或检测盒子中的任意一个，就不启用这条规则。不需要增加地图标签或组件。

配置检测盒子后，首次开局、FT 小局结束及再开局、整场结束或取消时，清理本组盒子内的散落装备、尸体和无人骑乘的马；保留所有存活角色、手持装备、正在骑乘的马和地图武器架。边界后一秒内继续短暂扫尾，处理尸体淡出后产生的掉落物；单项清理失败会重试，失败未处理完时不开始新局。没有检测盒子时不执行区域清理，不使用全场景删除接口。

本项目使用的原版 Custom / Community 专服大厅保留原有服务逻辑，并按角色实体对死亡回调去重，避免清尸体再次扣减 AI 存活数、重复计算击杀或助攻。其他扩展替换了大厅类型时保留其组件，尸体回退到原生 10 秒寿命，散落装备和无人马的区域清理仍继续。

同一玩家不能同时预约多组或参加 PvP。每组复用自己的玩家/AI 私有队伍，结束后恢复玩家及原坐骑的队伍；失败的清理步骤保留引用并重试。AI 及其坐骑在取消时清理；区域内尸体由对局边界立即清理，其他尸体仍使用本决斗场景的 **10 秒消失设置**。这不会要求修改 Native 模块或安装客户端 Mod。

当前仅完成编译、离线行为和接线检查，真实命中、导航、AI 战斗、动态碰撞、原版客户端提示及联网同步需实机验收。场景和游戏安装目录未自动修改。

## 构建

使用当前 Bannerlord Dedicated Server 的 DLL，设置 `MB_SERVER_PATH` 后构建整个 `AdimiDuel_Server.sln`。默认构建仅输出本地文件，不再自动覆盖专服目录；只有显式指定 `DeployToBannerlordServer=True` 才复制模块文件。`BannerlordValidationBuild=True` 模式禁止部署，并要求将输出和中间文件指向专服之外的绝对路径。
